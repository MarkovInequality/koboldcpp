# qwen38-calib-v1: the calibration set for the Qwen3.8-27B Hessians

These scripts build the calibration set that `hessian-collect` runs through Qwen3.8-27B to collect the input
Hessians (see `../README.md` and `plans/hessian_collection_plan.md`). The set has 1.0M counted tokens that look
like the model's real use in OpenCode and plain chat:

- Most documents go through Qwen3.8's own chat template.
- Most replies are generated by the model itself (`Qwen3.8-27B-HQ8_0.gguf`), thinking included.
- A tenth of the set comes from full OpenCode sessions the model drove on real repositories.

A further 10 % is held out, split by source unit (a conversation, a book, an article, a repo), so no text lands
on both sides.

## The dataset (`dataset/`)

The kept output, written here by `split.py` and `opencode/evalset.py`. It is git-ignored (`dataset/.gitignore`): it holds
third-party text under the licences of its sources, and `eval-opencode.jsonl` holds the user's own OpenCode
sessions.

| file | contents |
|---|---|
| `calib.jsonl` | 376 documents, one JSON object per line: `id`, `category`, `unit` (the split unit), `templated`, `text`, and optionally `count` |
| `heldout.jsonl` | 45 held-out documents, same format |
| `calib-heldout.txt` | the held-out texts, concatenated. They contain the chat-template markers as text, so tokenize with special tokens parsed |
| `eval-opencode.jsonl` | 34 of the user's recorded Qwen3.8 OpenCode sessions, rendered as koboldcpp renders them. For evaluation only, never calibrated on |
| `manifest.json` | sources and their revisions, per-category counted and processed tokens, length histogram, drops, generation throughput, the OpenCode runs, and each file's sha256. The dataset tag used in the Hessian file is `qwen38-calib-v1:<sha256(calib.jsonl)[0:12]>` |

**Count spans.** `count` is a list of `[start, end)` token spans (tokenized with the model's vocab, special tokens
parsed, no BOS). Only these rows enter the Hessians; the other tokens are processed as context. Without `count`,
the whole document counts. The OpenCode documents use it to:
- count the ~11k-token shared system prompt in only three documents
- sample the late positions of long sessions

**Mix** (counted tokens):

| category | tokens | what the model sees | replies |
|---|--:|---|---|
| chat | 200k | WildChat and oasst2 prompts (English), ~30 % multi-turn | self |
| coding | 200k | WildChat and oasst2 code questions; explain, review, find the bug, write tests, or port a real file from the pinned repos | self |
| agentic | 100k | `hermes_reasoning_tool_use` converted to Qwen's tool-call format (final turn regenerated); short OpenCode tool-call episodes | self |
| math | 100k | NuminaMath-CoT problems, stratified over its sources, thinking on | self |
| multilingual | 100k | aya prompts and FineWeb-2 text in Chinese, ja, ko, es, fr, de, ru, ar, pt, vi; half raw, half as a task | self |
| long | 100k | 6–8k-token documents: a PG-19 excerpt, a long source file, or several Wikipedia articles, with a task | self |
| raw | 100k | untemplated FineWeb-Edu, Wikipedia, PG-19 and source files, 1–8k tokens | — |
| opencode | 100k | full OpenCode sessions on clones of the user's repos and the pinned public repos, up to 128k tokens | self, through OpenCode |

**Replies** use the GGUF's sampling defaults (temperature 1.0, top-p 0.95, top-k 20).
- **Thinking:** on for 75 % of prompts (xhigh 45 %, medium 15 %, low 15 %), off for 25 %.
- **Caps:** new tokens are capped at `min(6144, 8192 − prompt)`. A reply that hits the cap is kept, ending at the
  cap. It still has to pass the loop checks: no 64-token span three times, and a compression ratio under the
  threshold set from the first 200 replies.

## Requirements

- **Build:** `make LLAMA_CUBLAS=1 koboldcpp_cublas hessian-tokenize`.
  - `hessian-tokenize` is the tokenizer every script uses. It calls `llama_tokenize` exactly as `hessian-collect`
    does, so counts and spans match what the collector sees.
  - Don't tokenize through koboldcpp's `/api/extra/tokenize`: it writes into a shared static buffer, so concurrent
    calls corrupt each other and crashed its batch server.
- **Python:** any Python 3 with `pyarrow requests numpy jinja2 pyyaml`, as `PY` (`opencode/run.sh` reads it too;
  default `python3`).
- **`GEN_MODEL`:** the generator model's GGUF, `Qwen3.8-27B-HQ8_0.gguf` for `qwen38-calib-v1`. `serve.sh` serves it,
  `fetch.py` takes its chat template, the tokenizer loads it, and `split.py` records its name.
- **`USER_REPOS`:** the directory holding your own repos that `opencode/tasks.jsonl`'s `user:` entries name (airi,
  hegel-rust, neovim, remove-refusals-with-transformers, voicebox, xet-core). They're only cloned from, and
  `opencode/snapshot.py` checks they're unchanged afterwards.
- **OpenCode:** v1.18.32 on `PATH` (or `OPENCODE=<binary>`), for the OpenCode part. Your own OpenCode data and config
  are read from their XDG locations, `$XDG_DATA_HOME/opencode` and `$XDG_CONFIG_HOME/opencode` (default
  `~/.local/share` and `~/.config`).
- **`TMPDIR`** (default `/tmp`), outside `$HOME`: where `opencode/run.sh` puts each run's throwaway layer.
- **Resources:** about 3 GB of disk in `work/` (git-ignored) while building, and a 32 GB GPU.

## Building it

Run from `tools/hessian/calib/`, in this order. Everything temporary goes to `work/`.

```
export PY=python3                                  # with the packages above
export GEN_MODEL=/path/to/Qwen3.8-27B-HQ8_0.gguf
export USER_REPOS=/path/to/your/repos

$PY fetch.py                      # 1. sources -> work/sources/, pins revisions in sources.json
$PY prompts.py                    # 2. prompt list -> work/gen/prompts.jsonl
./serve.sh gen                    # 3. koboldcpp for generation (port 5002)
$PY generate.py                   # 4. replies -> work/gen/docs.jsonl (about 4.5 h)
$PY raw.py                        # 5. untemplated documents -> work/gen/raw_docs.jsonl
./serve.sh opencode               # 6. koboldcpp as the user runs it (port 5003)
opencode/setup.sh                 # 7. isolated OpenCode config, snapshot of what must not change
opencode/run.sh --user-config < /dev/null     # 8a. prompt check: a request with the user's own config,
opencode/run.sh e01-ripgrep-loc < /dev/null   #     one short task, and the comparison (see ../GUIDE.md)
$PY opencode/promptdiff.py work/opencode/captures/_user-config.jsonl work/opencode/captures/e01-ripgrep-loc.jsonl
opencode/run.sh < /dev/null       # 8. the OpenCode tasks -> work/opencode/docs.jsonl (about 6.5 h)
./serve.sh stop
$PY opencode/evalset.py           # 9. the user's sessions -> eval-opencode.jsonl
$PY techeval.py                   # 10a. the out-of-domain evaluation text -> dataset/tech-eval.txt
$PY decontam.py --eval ../../models/wiki.test.raw --eval dataset/tech-eval.txt   # 10. 13-gram filter against the evaluation texts
$PY split.py                      # 11. calib/heldout split, budgets, manifest -> dataset/
$PY stats.py                      # 12. the checks
./cleanup.sh                      # 13. removes work/
python3 stats.py --after-cleanup  #     work/ gone, kept files match the manifest
```

Every step can be rerun. `generate.py` and `opencode/run.sh` resume where they stopped.

## The scripts

### Shared

- **`common.py`:** paths, the category targets (`TARGETS`, `HELDOUT`), document length limits (8192; 131072 for
  OpenCode), jsonl helpers, the seed, and a minimal GGUF key reader.
- **`kcpp.py`:** the koboldcpp client and renderer.
  - `render()` / `render_request()` build a prompt exactly as koboldcpp's `format_jinja` does: sandboxed jinja
    with `trim_blocks`/`lstrip_blocks`, its `tojson`, message clean-up and the reasoning-effort kwargs.
  - `render_turn()` renders a reply the way it appears in the next request's history.
  - `tokenize()` / `detokenize()` run through `hessian-tokenize`.
  - `complete()` posts to `/v1/completions`. A dead server is restarted through `serve.sh`, and a full request
    queue (503) is retried.
- **`sources.json`:** every source, pinned. Hugging Face datasets by revision (with the files and columns read);
  PG-19 books; code repos by commit, with the licence found. `fetch.py` fills in any revision left `null`.
- **`serve.sh gen|opencode|stop`:** koboldcpp serving HQ8_0, with a pid file.
  - `gen`: 8 parallel slots, 64k shared context, q8_0 KV, FFN of the last 7 layers in RAM.
  - `opencode`: the user's settings (jinja, tools, q5_1 KV, MTP), 128k context, FFN of 14 layers in RAM (`OT=`
    overrides the placement).

### Generated categories

- **`fetch.py [--only NAME,...]`:** downloads slices of the sources. Parquet shards are read by row group over
  HTTP range requests, so multi-GB shards are never downloaded whole. PG-19 books come from DeepMind's bucket. The
  code repos are shallow clones at pinned commits, and a repo is skipped unless a permissive licence is found. It
  also extracts the chat template from the GGUF.
- **`prompts.py`:** the prompt list for every generated category, sampled with a fixed seed.
  - **Filters:** WildChat moderation, dedup, per-user and per-prefix caps; oasst2 best-ranked paths.
  - **Code tasks** on repo files follow the language shares (TS/JS 25 %, Python 25 %, Rust 20 %, C/C++/CUDA 20 %,
    other 10 %). "Find the bug" tasks flip one operator.
  - **Hermes** tool conversations are converted to Qwen's format.
  - **Language** and thinking mixes are sampled per prompt.
  - **Held-out:** each prompt carries its split unit and held-out flag.
- **`generate.py [--workers 8] [--categories ...] [--recover-capped]`:**
  - **What it does:** renders each prompt, generates the reply through the server, and writes the document
    (prompt + reply + `<|im_end|>`, or ending at the cap). Multi-turn conversations are generated turn by turn.
  - **Filling:** buckets (category, source, language) fill to their share of the target; the held-out side is
    pooled per category.
  - **Checks per reply:** koboldcpp's prompt token count equals ours, and the loop checks pass.
  - **Resume and control:** resumable. One instance at a time (lock file). `SIGUSR1` finishes the replies in
    flight and exits. `--recover-capped` rebuilds capped replies from `work/gen/completions.jsonl`.
- **`raw.py`:** the untemplated documents (raw category and multilingual's raw half). They are cut to lengths drawn
  from 1–8k tokens, and short source documents of one kind are concatenated.

### OpenCode (`opencode/`)

- **`tasks.jsonl`:** 11 sessions (3 of them long) and 24 short tool-call episodes. Each gives the repo, reasoning
  effort, prompt, follow-ups, an optional injected bug, and whether it counts the shared prefix.
- **`setup.sh`:** the isolated XDG dirs and OpenCode config, a copy of the user's own config for comparison, and a
  snapshot (`snapshot.py`) of what must not change.
  - The config uses the user's own provider and model names: OpenCode writes them into its system prompt.
  - Context is 131072.
  - The provider's timeouts are off or 1 h: koboldcpp sends a tool-mode reply only when it's complete, and OpenCode
    would retry anything over 5 minutes.
  - The permission deny list covers `git push`, `sudo`, `curl`/`wget` and package installs, plus anything outside
    the working copy.
- **`run.sh [--user-config] [TASK_ID ...]`:** runs the tasks one at a time.
  - **Sandbox:** each run is in a user and mount namespace that overlays `$HOME` with a throwaway layer in `$TMPDIR`,
    with the isolated XDG dirs mounted through. Nothing the agent writes, its working copy included, reaches the
    real files. The layer is deleted after the run, also on failure or interrupt.
  - **Capture:** the proxy records every request, and `render.py` turns the capture into documents.
  - **Options:** `--user-config` makes one request with the user's config, to compare prompts. `UPSTREAM=`,
    `OPENCODE_TIMEOUT=` and `OPENCODE_DEBUG=1` help with debugging.
  - **Stdin:** start it with `< /dev/null`. `opencode run` reads a piped stdin into its message and waits for EOF.
- **`inside.sh`:** one task inside the sandbox: a fresh clone without remotes (and the injected bug, committed),
  then `opencode run` and its follow-ups in the same session.
- **`proxy.py PORT UPSTREAM CAPTURE [CONTEXT]`:** the logging proxy between OpenCode and koboldcpp.
  - Streams replies through and records `{request, response}` per request.
  - Returns OpenAI's `context_length_exceeded` when prompt + `max_tokens` would exceed the context. koboldcpp
    would otherwise silently cut the prompt's start, and OpenCode never compacts on its own because koboldcpp's
    tool replies carry no `usage`.
- **`render.py TASK_ID`:** one task's capture into documents.
  - **Chains:** a compaction or a subagent starts a new history, so each chain of requests is rendered as its last
    request plus that request's reply, as the template renders it in history.
  - **Checks:** every request's rendered prompt must match koboldcpp's prompt size (from its log:
    `CtxLimit − Generated`), and earlier reasoning must be present. Tool calls are tallied.
  - **Output:** documents and their count spans go to `work/opencode/docs.jsonl`, checks to `checks/<id>.json`.
- **`evalset.py [CAPTURE]`:** renders the user's recorded Qwen3.8 sessions from a copy of `opencode.db` (the
  original is only read). The system prompt and tools come from a capture of the current OpenCode version.
- **`promptdiff.py A.jsonl B.jsonl`:** compares the prompt in two captures: the tool list, each tool's schema, and
  the system prompt as a diff. For the `--user-config` check: the probe against a calibration task should differ
  only in the working-directory line.
- **`snapshot.py OUT | --compare BEFORE`:** row counts of the user's `opencode.db` (read from a copy), hashes of
  the OpenCode config dir, and HEAD and `git status` of the `user:` repos in `USER_REPOS`, compared after the runs.

### Finishing

- **`techeval.py [--rev REV] [OUT]`:** builds `tech-eval.txt`, the out-of-domain evaluation text: the repo's
  top-level docs (`README.md`, `docs/*.md`, `tools/*/README*.md`) cut at 115,000 bytes, then the first 95,000 bytes of
  `src/llama-model.cpp`, read from git at `REV`. The default `7957c3ad6` reproduces the original; any revision serves
  the same purpose, since the calibration set takes no text from this repo.
- **`decontam.py --eval TEXT [--eval TEXT...] [FILES]`:** drops documents that share a word 13-gram (lower-cased,
  whitespace collapsed) with the evaluation texts (`wiki.test.raw` and `dataset/tech-eval.txt` for `qwen38-calib-v1`)
  or the GSM8K and MATH test sets.
- **`split.py`:** writes the kept dataset.
  - **Generated documents:** taken per bucket in generation order up to the targets.
  - **OpenCode:** each session's longest chain is kept (a document costs its whole length in every Hessian pass,
    counted or not). Counted positions are thinned in 512-token blocks at a fixed stride to the category budget:
    long sessions' positions ≥ 32k get 40 %, other sessions the rest, and the episodes half of agentic. The three
    documents that count the shared prefix keep it whole.
  - **Output:** the calib/heldout split by source unit, and the manifest.
- **`stats.py [--after-cleanup]`:** the checks.
  - per-category targets ±10 %
  - document lengths and count spans
  - one special token per template marker
  - ≥ 25 % of counted tokens at positions ≥ 4096
  - shared-prefix share 15–25 %
  - episode tool mix
  - token counts against koboldcpp's for every request
  - earlier reasoning present
  - no 13-gram overlap
  - the user's OpenCode data and repos unchanged

  With `--after-cleanup`: the work dir is gone and the kept files match their hashes.
- **`cleanup.sh`:** stops a server if one is running, removes `work/` and leftover sandbox layers, and lists the
  kept dataset.

## Build notes (v1)

- **Throughput:** generation ran at ~70 tok/s aggregate over 8 slots; about 44 % of generated tokens were capped
  replies. The OpenCode runs went one request at a time at 15–24 tok/s: koboldcpp doesn't batch requests with
  tools.
- **Sessions ran long.** At 128k they reached 17k–123k tokens, s01 with three compactions, and together counted far
  more than the budget; `split.py` thins them.
- **One check fails:** the episodes' tool mix. read is 17 % against a 25 % target and grep 18 % against 11 %. Over
  all OpenCode runs read is the largest share, about 32 %.
- The details, and every deviation from the plan, are in the plan's Implementation record.
