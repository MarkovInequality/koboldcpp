# Plan: Full input Hessians for Qwen3.8-27B (calibration set and collector)

Status: implemented 2026-09-27/28, uncommitted; see "Implementation record". Follows up `plans/gptq_rotated_quantizer_plan.md`: its GPTQ uses
`H = R·diag(v)·Rᵀ` built from an imatrix, and its Future work names the richer Hessians (full
covariance, low-rank). This plan produces the data for them. Using the full `H` in the quantizer is
the next plan (see "What comes next").

## Summary

The quantized model will be used in two ways: in OpenCode (agentic coding, long contexts) and for
plain chat. This plan builds a 1.0M-token calibration set that looks like those inputs. Most of it
goes through Qwen3.8's own chat template, and most of the replies are generated by the model
itself, 15 % of it through OpenCode.

It then runs the set through `Qwen3.8-27B-HQ8_0.gguf` and stores, for every distinct GEMM input,
the full Gram matrix `G = Σ x·xᵀ` of the unrotated input. That is GPTQ's Hessian up to scale.

**The output file:**
- It's an imatrix GGUF with one more tensor kind.
- Every weight keeps its `<name>.in_sum2` / `<name>.counts`, so the file also works as an ordinary
  imatrix.
- Each distinct input adds a `<owner>.in_gram` F32 `[n, n]` tensor. The Grams total 101 GB.

**The collector** is a new tool, `hessian-collect`:
- A small graph hook records each weight GEMM's input node.
- The tool accumulates `G` on the GPU with cuBLAS SYRK, over 8 passes of 8 layers each, because the
  Grams fit in neither VRAM nor RAM at once.

The calibration set and the Hessian are kept. Everything else the work creates is deleted once it
has been used (see "Storage").

## Goal

1. **Calibration set `qwen38-calib-v1`,** 1.0M counted tokens for the Hessians plus 10 % more held
   out.
   - Most documents are chat-templated with Qwen3.8's own template.
   - Most assistant turns are generated by `Qwen3.8-27B-HQ8_0.gguf`, thinking included. That covers
     the OpenCode sessions and tool-call episodes, which the model drives itself through OpenCode.
   - Each document is its own sequence starting at position 0: at most 8192 tokens, or 65536 for
     OpenCode.
2. **`hessian-collect`** runs the set through a GGUF model and writes one file with, for every
   weight the forward pass uses:
   - `<w>.in_sum2` (F32 `[n, 1]`) and `<w>.counts` (F32 `[1, 1]`), with the same meaning and
     layout as upstream `llama-imatrix`'s GGUF output
   - the full Gram of its input, stored once per distinct input and shared through aliases
3. **The Grams are in the unrotated input space,** even when the model is an HQ file. So they
   serve any HQ seed and any non-HQ type.
4. **`--imatrix <hessian file>` works as today.** The imatrix loader stops reading whole files into
   RAM, and the diagonal-GPTQ output stays byte-identical to that from an imatrix with the same
   `in_sum2`.
5. **The 27B run** fits this box in about 2–2.5 hours, and can resume after an interruption.
6. **Temporary files are deleted** once they've been used. The calibration set, the evaluation set
   and the Hessian are kept.

Out of scope:
- using the full `H` in the quantizer (next plan)
- MoE / `MUL_MAT_ID` Grams (the tool refuses them; Qwen3.8-27B is dense)
- the MTP layer `blk.64`, which a normal forward pass doesn't run (Unsloth's imatrix has no
  entries for it either)
- vision inputs (image tokens do reach the LLM layers; a later version could add mtmd documents)
- sequential GPTQ, which collects each layer's inputs through the already-quantized earlier layers

## Facts this plan rests on (checked 2026-09-26/27)

**Model** (`Qwen3.8-27B-bf16.gguf` metadata; the HQ8_0 file has the same tensors):
- arch `qwen35`, 64 layers plus the MTP layer `blk.64`
- `n_embd` 5120, `n_ff` 17408, 24 heads × 256, 4 KV heads, SSM inner size 6144
- `full_attention_interval` 4: layers 3, 7, …, 63 are attention (16), the other 48 are Gated DeltaNet

| layer kind | input (width) | weights reading it | owner (loader order) |
|---|---|---|---|
| SSM | `attn_norm` output (5120) | `attn_gate`, `attn_qkv`, `ssm_alpha`, `ssm_beta` | `attn_gate` |
| SSM | DeltaNet output (6144) | `ssm_out` | `ssm_out` |
| attention | `attn_norm` output (5120) | `attn_k`, `attn_q`, `attn_v` | `attn_k` |
| attention | gated attention output (6144) | `attn_output` | `attn_output` |
| both | `post_attention_norm` output (5120) | `ffn_gate`, `ffn_up` | `ffn_gate` |
| both | SwiGLU output (17408) | `ffn_down` | `ffn_down` |
| — | `result_norm` (5120) | `output` | `output` |

- **Weight count:** 48·8 + 16·7 = 496 weights in the layers, which matches Unsloth's imatrix
  (992 tensors), plus `output.weight`.
  - `ssm_alpha` / `ssm_beta` read the same node as `build_qkvz` (`src/models/qwen35.cpp:358–369`).
- **Gram size per layer:** 2·5120² + 6144² + 17408² = 393.2M floats, which is 1.573 GB in F32.
  - 64 layers + `output`: **100.8 GB**. `ffn_down` is 77 % of that.
  - One copy per weight instead of per input would add 25.2 GB; packed triangles would take
    50.4 GB.
- **`imatrix_unsloth.gguf`:** `imatrix.datasets = ['unsloth_calibration_dataset']`,
  `chunk_size` 8192, counts 1,149,614 tokens. It has no `output` entry and no `blk.64` entries.
  - **Unsloth's description of that set:** "high-quality, hand-curated and cleaned data", refined
    for "agentic coding, chat, and multilingual performance".
  - **Their docs also say** that "using text only calibration datasets is not effective for
    instruct models" [Unsloth].
- **Chat template** (from the GGUF, Unsloth-patched):
  - thinking is on by default, with `reasoning_effort` ∈ {xhigh (default), medium, low}, which
    injects a system instruction
  - `enable_thinking=false` emits an empty think block
  - `preserve_thinking` renders earlier turns' `reasoning_content`, and defaults to on
  - tool calls render as `<tool_call><function=…><parameter=…>` XML
  - GGUF sampling defaults: temp 1.0, top_p 0.95, top_k 20

**The user's OpenCode use:**
- **Setup:** OpenCode v1.18.32 (`~/.opencode/bin/opencode`).
  - One koboldcpp provider in `~/.config/opencode/opencode.json`, with no plugins and no global
    instructions.
  - Reasoning effort `medium` by default, with `xhigh` and `low` variants.
  - koboldcpp runs with `jinja` and `jinja_tools` on, 262k context and a q5_1 KV cache
    (`~/AI/qwen3/Qwen3.8-27B-UD-Q4_K_XL.kcpps`).
- **Recorded sessions:** `~/.local/share/opencode/opencode.db` holds 49 Qwen3.8 sessions, with a
  median of about 45k tokens of content each. 31 of them ran in this repository.
- **Tool calls in those sessions:** bash 51 %, read 25 %, grep 11 %, edit 8 %, glob 2 %; todowrite,
  task, webfetch, write, question and skill about 1 % or less each (1926 calls).
- **What OpenCode sends** (tested with a mock server that streams like koboldcpp, in isolated
  XDG dirs, one tool step and one follow-up turn):
  - every earlier assistant turn goes back with its `reasoning_content`, within a tool loop and
    across user turns
  - `reasoning_effort` is passed on every request
  - each session starts with a separate short title-generation request
  - the system prompt plus its 10 tool schemas render to about 44k characters, roughly 11k
    tokens, at the start of every request
- **How koboldcpp renders it:** `format_jinja` (`koboldcpp.py:4018`) passes messages to the
  template unchanged.
  - It uses `ImmutableSandboxedEnvironment` with `trim_blocks` and `lstrip_blocks`, its own
    `tojson` (`ensure_ascii=False`) and a no-op `raise_exception`, with `bos_token = eos_token = ""`.
  - It streams reasoning as `delta.reasoning_content`.
  - `--parallelrequests` batches only plain text requests.
- **So the model sees every step's reasoning in history, and each request is a prefix of the
  next.** A session's last request plus its response is exactly the token sequence the model
  processed over the whole session.

**Engine** (this fork):
- **HQ inputs:** a rotated weight's GEMM reads `RHT(x)` (`rotate_input_if_rotated`,
  `src/llama-graph.cpp:1513`).
  - After the RHT runs, `x` can be freed and its memory reused by the GEMM's own output. So a
    callback on the GEMM can't read `x`.
  - It can't reliably tell which other weights share that input either, once the scheduler copies
    inputs between splits.
  - Hence the graph hook in §4.
- **The eval callback can't stop a graph.** Returning `false` ends only the current split
  (`ggml/src/ggml-backend.cpp:1782`).
- **Output rows:** Qwen3.8 selects them after the last layer (`src/models/qwen35.cpp:215`), so
  every layer sees every token whatever the logits flags.
  - Qwen3 (the 0.6B test model) selects them inside the last layer (`src/models/qwen3.cpp:114`).
  - Qwen3-0.6B also ties its embeddings: its LM head is `token_embd.weight`.
- **Hybrid memory:** it splits a batch into ubatches with equal tokens per sequence (`split_equal`,
  `src/llama-memory-hybrid.cpp:89`), so one `llama_decode` can run several graphs.
- **Op offload:** with a batch of at least 32 (`GGML_OP_OFFLOAD_MIN_BATCH`), a GEMM whose weight is
  in RAM runs on the GPU, and the weight is copied over once per ubatch.
- **Available tools:** upstream `llama-imatrix` at 53ed051 was built in
  `build-hq/upstream-llama/build/bin/` (deleted 2026-09-28). The fork itself has no imatrix tool.
- **`common_imatrix_load`** reads every tensor of a file into RAM (`no_alloc = false`).

**Machine:**
- RTX 5090 32 GB (the desktop uses 2.6 GB)
- 30 GB RAM + 8 GB swap, 8 cores
- 288 GB free disk
- memlock limit 64 MB (`ulimit -l`), so `--mlock` can't pin model weights

**HQ8_0 sizes:**
- FFN weights: 64 × 284 MB = 18.2 GB
- other layer weights: 7.7 GB
- `output`: 1.35 GB
- `token_embd`: 1.35 GB, on the CPU (it's a `get_rows`)

## Design

### 1. The calibration set

**Size: 1.0M counted tokens for the Hessians, plus 10 % more held out.**
- A document's *counted* tokens are the ones that enter the Grams; the rest are processed only as
  context (§2, count spans).
- Unsloth used 1.15M tokens for this model.
- 1.0M tokens is at least 57 tokens per dimension for the widest input (17408).
- The full-covariance GPTQ that overfit on Qwen3-0.6B had 6.5 per dimension (20k tokens, width
  3072: in-sample output error 0.207 against 0.409 held out).
- Phase 5's split-half check reports whether 1.0M is enough.

**Mix** ("self" means the assistant turns are generated by `Qwen3.8-27B-HQ8_0.gguf`):

| category | share | tokens | what the model sees | assistant turns |
|---|--:|--:|---|---|
| chat | 20 % | 200k | real user prompts, ~30 % multi-turn: writing, advice, explanation, role-play, summarizing a supplied text | self |
| coding | 20 % | 200k | code questions; explain / review / fix / write tests for a real source file supplied in the prompt | self |
| agentic / tool use | 10 % | 100k | 50k: tool schemas + multi-step tool conversations in Qwen's XML tool format; 50k: short OpenCode tool-call episodes (§1.2) | tool dataset: as in the source, final turn self; episodes: self |
| math / STEM reasoning | 10 % | 100k | competition and school math problems | self, thinking on |
| multilingual | 10 % | 100k | prompts and prose in Chinese (most), ja, ko, es, fr, de, ru, ar, pt, vi | self, same language |
| long context | 10 % | 100k | 6–8k-token prompts: a book excerpt, a long source file, or several articles plus a question | self |
| raw text | 10 % | 100k | no template: web, encyclopedic, fiction, code files | — |
| OpenCode sessions | 10 % | 100k | full OpenCode sessions on copies of the user's repos and the pinned public repos, three of them running to 40–64k tokens (§1.1) | self, through OpenCode's own system prompt and tools |

**Programming languages.** Code tokens are weighted toward the user's languages. This applies to
the pinned repos' files, and to code prompts from the chat sources, classified by their code fences
and keywords.

| language | share | pinned repos |
|---|--:|---|
| TypeScript / JavaScript | 25 % | `honojs/hono`, `colinhacks/zod`, `vitejs/vite`, `expressjs/express` |
| Python | 25 % | `psf/requests`, `pallets/flask`, `encode/httpx`, `pydantic/pydantic` |

| other (Go, Java, Kotlin, shell, SQL) | 10 % | `spf13/cobra`, `google/gson`, `square/okhttp` |

- **CUDA stands in for the user's main codebase,** this repo's ggml C++/CUDA. It comes from projects
  that share no code with this one, so tech-eval stays clean. `fetch.py` checks every repo's
  licence file (BSD-3-Clause expected for the two CUDA ones) and skips a repo whose licence isn't
  permissive.
- **No library that this repo vendors** (nlohmann/json, stb, miniaudio, cpp-httplib), since
  tech-eval's C++ comes from this repo.
- **The OpenCode sessions and episodes** run on these repos as well as on the user's own, which
  lean the same way: `airi` and `voicebox` are TypeScript, `hegel-rust` and `xet-core` Rust,
  `neovim` C/Lua, and `voicebox` and `remove-refusals-with-transformers` Python.

**Not used:**
- `bigcode/the-stack-smol`: gated behind its terms of use; the pinned repos replace it
- Bartowski's `calibration_datav3`: no licence stated
- LMSYS-Chat-1M: its own restrictive licence

**Why most of it is templated and self-generated:**
- An instruct model's activations depend on its template tokens and on its own style of answer
  [Unsloth].
- Bartowski found that a 2:3 ratio of prose to templated conversations worked best for imatrix
  calibration [Bartowski].
- Williams et al. show that calibration data generated by the model itself works as well as or
  better than real data for quantization and pruning [Williams 2025].
- Prose and code still make up about a third of the tokens, but mostly inside a templated task
  (summarize, review, answer from documents), which is how a chat model usually sees them.
- Math, multilingual and raw text aren't part of the user's usage. They keep the quantization from
  giving up abilities that the rest of the set doesn't exercise.

**Generation** (every category except OpenCode):
- **Server:** koboldcpp (this fork) with `--parallelrequests 8`, serving `Qwen3.8-27B-HQ8_0.gguf`,
  which is at KL 0.0004 against BF16.
- **Prompts:** rendered in Python from the template string in the GGUF, with
  `add_generation_prompt=True`, exactly as koboldcpp's `format_jinja` does (see Facts). Plain
  `jinja2` defaults would render different whitespace. The rendered prompts are sent to the raw
  completion endpoint.
- **The document is prompt + completion + `<|im_end|>`,** exactly the text the model processed. No
  re-parsing of reasoning or tool calls happens.
- **Thinking mix:** on for 75 % (xhigh 45 %, medium 15 %, low 15 %), off for 25 %. Plain chat in
  the user's koboldcpp runs at the template's default, xhigh.
- **Sampling:** the GGUF defaults. New tokens are capped at `min(6144, 8192 − prompt tokens)`.
- **Bad generations are dropped and counted in the manifest:**
  - responses that hit the cap before `<|im_end|>`
  - responses with repetition loops (a repeated 64-token span, or a compression ratio above a
    threshold set from the first 200 responses)
- **Special tokens:** koboldcpp's reported `usage.prompt_tokens` must equal our tokenizer's count
  for every document. Otherwise koboldcpp has tokenized `<|im_start|>` etc. as plain text, and the
  reply was conditioned on a prompt the model never sees in use.
- **Multi-turn:** conversations are generated turn by turn and rendered with the template's
  defaults.
- **Volume:** about 450k generated tokens. Phase 1 measures the throughput. At 150 tokens/s
  aggregate that would take under an hour.

#### 1.1 OpenCode sessions (100k)

- **Server:** koboldcpp serving HQ8_0 with the user's settings (`jinja`, `jinja_tools`, flash
  attention, q5_1 KV cache), a 65536-token context, and one session at a time.
- **Isolation:** OpenCode runs with its own `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`
  and `XDG_STATE_HOME` under `tools/hessian/calib/work/opencode/`. The user's config and session
  database are never touched.
- **The config mirrors the user's:**
  - the same provider type, the same per-variant `reasoningEffort` options, and a model id
    containing `Qwen3.8`. OpenCode ships several system prompts and picks one by model id, so a
    different name could silently change the prompt.
  - The base URL points at the logging proxy below.
  - `limit.context` / `limit.output` are set to koboldcpp's context, so OpenCode compacts the
    session itself. Otherwise koboldcpp would silently cut an over-long prompt.
  - **Check:** the captured system prompt and tool list match those of one request made with the
    user's own config.
- **Permissions:**
  - allowed: file edits and shell
  - denied: `git push`, `sudo`, `curl`/`wget`, package installs (`npm`/`pnpm`/`yarn` install or
    add, `pip install`, `cargo install`/`add`), and anything outside the working copy
  - Cargo runs offline (`CARGO_NET_OFFLINE=true`), so builds and tests use only what's already
    cached.
- **Working copies:** every session runs in a fresh clone of one repo, in
  `tools/hessian/calib/work/opencode/copies/`, with the git remotes removed.
  - The repo is either one of the user's own (`~/Sandbox/airi`, `neovim`, `hegel-rust`,
    `voicebox`, `xet-core`, `remove-refusals-with-transformers`) or one of the pinned public repos.
  - Sessions never run in the originals or in this repository.
- **Tasks:** about 10 sessions, spread over the repos, the language shares above, and the kinds of
  work a coding agent gets:
  - explain a module or answer a question about the code
  - find and fix a bug
  - add a small feature with tests
  - refactor
  - write docs
  - review a diff
  - Phase 1 drafts the list, and the user reviews it before any session runs.
  - About a third of the sessions get 1–2 follow-up turns (`opencode run -s <session>`).
- **Long sessions:** three of the tasks are open-ended (a multi-file feature, a survey of a large
  codebase such as neovim or vite) and run to 40–64k tokens, where the user's real sessions spend
  much of their time.
- **Command:** `opencode run --pure -m Calib/Qwen3.8-27B-HQ8_0 --variant <v> --dir <copy> --auto
  "<task>"`, with variants in the user's proportions: medium 70 %, xhigh 25 %, low 5 %.
- **Capture:** a logging proxy between OpenCode and koboldcpp stores every
  `/v1/chat/completions` request (messages, tools, reasoning effort) and its streamed response.
- **Rendering:** a session's document is its last request, rendered as koboldcpp does, plus that
  request's response and `<|im_end|>`. That's the whole session as the model processed it (see
  Facts).
  - **Check:** for every captured request, the rendered prompt's token count equals koboldcpp's
    `usage.prompt_tokens`, and every earlier turn's reasoning appears in it.
- **Length:** at most 65536 tokens, cut at the last step boundary that fits.
- **Counted tokens (§2's count spans):**
  - **The shared prefix** (system prompt + tool schemas, about 11k tokens, identical in every run
    up to its environment block) gives identical activations wherever it repeats. It's counted in
    only three documents (two sessions, one episode), about 20 % of the OpenCode-related counted
    tokens. That's its share in the user's real sessions: about 11k of a median of about 56k.
  - **Long sessions** count only positions ≥ 32768. Their first half is context, so they add
    late-position activations without over-weighting early ones.

  | part | counted |
  |---|--:|
  | the late halves of the 3 long sessions | ≈ 35k |
  | 6–8 sessions of 12–32k, after the shared prefix | ≈ 45k |
  | the shared prefix, counted twice | ≈ 20k |

- **Rate:** measured in Phase 1. HQ8_0 doesn't fit the GPU entirely, so decoding is partly
  CPU-bound. At an assumed 12 tokens/s, with koboldcpp reusing the shared prefix between requests,
  the sessions take roughly 2–3 hours.

#### 1.2 OpenCode tool-call episodes (agentic, 50k)

Many short OpenCode runs with the same setup, repos, capture, rendering, checks and cleanup as
§1.1, built for breadth rather than length:
- **Size:** 1–6 tool steps each, 12–20k tokens including the shared prefix, with 1–3k counted after
  it. That's about 20–25 episodes, one of which also counts the shared prefix.
- **Tool mix:** prompts are chosen so the calls land close to the user's real distribution: bash
  about 50 %, read 25 %, grep 11 %, edit 8 %, and glob, todowrite, task and write for the rest.
  - For example: "find where X is defined", "run the tests and report failures", "rename Y in this
    file", "list the TODOs in src/".
  - There are no webfetch episodes, since the network is denied.
- **Failed calls are kept:** an unknown tool, bad arguments, or a failing command followed by the
  model's retry. The quantized model has to handle those too.
- **Cost:** about 1–2 hours of generation.

**Lengths:**
- Chat 0.5–6k tokens, coding 1–8k, long context 6–8k.
- Raw text is cut into documents whose lengths are spread over 1–8k.
- OpenCode episodes 12–20k, sessions 12–64k.
- **Target:** at least 25 % of counted tokens at positions ≥ 4096, so late-position activations
  (attention sinks, DeltaNet state growth) are represented.

**Keeping the evaluation texts clean:**
- Drop any document that shares a 13-gram with `wiki.test.raw` or `tools/hessian/calib/dataset/tech-eval.txt`, after
  lower-casing and collapsing whitespace.
- Take no text from this repository, since tech-eval is built from it. No OpenCode run happens
  here.
- The same 13-gram filter runs against the GSM8K and MATH test sets, since NuminaMath-CoT includes
  problems from both benchmarks.

**Held out:** 10 % of each category is never used for Hessians. It's written as
`calib-heldout.txt` for later KL runs on in-distribution text.
- **The split is by source unit, not by document:** a WildChat or oasst2 conversation, a PG-19
  book, a Wikipedia article, and a whole repo. A held-out repo is held out for the coding tasks,
  the OpenCode sessions and the tool-call episodes alike. Otherwise the same text lands on both
  sides.

**Evaluation set:**
- **What:** `evalset.py` renders the user's recorded Qwen3.8 OpenCode sessions from `opencode.db`
  (opened read-only) into `eval-opencode.jsonl`.
- **How:** the messages, reasoning, tool calls and tool results come from the database. The system
  prompt and tool schemas come from the capture of the current OpenCode version (older sessions
  may have had slightly different ones).
- **Use:** it's never calibrated on. It's the next plan's main measure of the user's real use, and
  its overlap with tech-eval doesn't matter there.

**The dataset files** (kept, see "Storage"):
- `calib.jsonl`: one document per line, `{"id", "category", "unit", "templated", "text", "count"}`.
  `unit` is the split unit. `count` is a list of `[start, end)` token spans; it's omitted when the
  whole document counts.
- `heldout.jsonl` and `calib-heldout.txt`
- `eval-opencode.jsonl`
- `manifest.json`: sources and their revisions, per-category counted and processed tokens, the
  length histogram, drop counts, generation throughput, and each file's sha256

### 2. What is collected

- **The Gram:** for each distinct GEMM input `x` of width `n`, `G = Σ_t x_t·x_tᵀ` over every
  counted row the GEMM processes. It's a raw sum, like `in_sum2`: `E[xxᵀ] = G / count`, and it's
  GPTQ's `H = 2·XXᵀ` up to scale.
- **The input is taken before rotation** (the `x` passed to `build_lora_mm`, not `RHT(x)`), so `G`
  is seed-independent. The HQ quantizer forms `R·G·Rᵀ` with the file's seed, as it does for
  `diag(v)` today.
- **Uncentred,** as GPTQ uses it. `in_sum2 = diag(G)` by construction.
- **Count spans:** a document's tokens count unless its `count` field limits them to a list of
  `[start, end)` spans. Uncounted tokens are still processed, so later tokens see the right
  context, but their rows don't enter any Gram.
  - The dataset uses this for OpenCode's shared prefix and for the first half of long sessions.
    Phase 5 uses it for its position check.
  - Each ubatch's rows are contiguous per sequence, so a span is one SYRK on a row range.
- **`output.weight`** is the exception to counting every token. Its input exists only at positions
  that request logits, so the tool requests every 8th counted position (`--output-stride 8`).
  - That gives about 125k rows (24 per dimension).
  - The logits buffer is 1 GB instead of 8 GB per 8192-token ubatch.
  - Neither upstream `llama-imatrix` (by default) nor Unsloth's imatrix covers this weight.

### 3. File format

A GGUF written the way `llama-imatrix` writes its own. Tensors are ordered by (layer, name), as in
`weight_name_comparer`, so each pass writes one contiguous byte range.

```
general.type                = "imatrix"
imatrix.datasets            = ["qwen38-calib-v1:<sha256[0:12]>"]
imatrix.chunk_count         = <documents>
imatrix.chunk_size          = 65536                     # longest sequence
hessian.version             = 1
hessian.source_model        = "Qwen3.8-27B-HQ8_0.gguf"
hessian.alias.names         = ["blk.0.attn_qkv.weight", "blk.0.ssm_alpha.weight", ...]
hessian.alias.owners        = ["blk.0.attn_gate.weight", "blk.0.attn_gate.weight", ...]
hessian.layers_done         = u8[65]                    # 64 layers + output; resume bookkeeping
hessian.complete            = bool

blk.0.attn_gate.weight.in_sum2   F32 [5120, 1]
blk.0.attn_gate.weight.counts    F32 [1, 1]
blk.0.attn_gate.weight.in_gram   F32 [5120, 5120]      # owner: attn_gate, attn_qkv, ssm_alpha, ssm_beta
blk.0.attn_qkv.weight.in_sum2    F32 [5120, 1]
blk.0.attn_qkv.weight.counts     F32 [1, 1]
...
blk.0.ffn_down.weight.in_gram    F32 [17408, 17408]
...
output.weight.in_gram            F32 [5120, 5120]
```

- **One Gram per distinct input:** that's what the Hessian belongs to, and GPTQ factors each input
  once. A copy per weight would add 25.2 GB.
- **Lookup:** a weight's Gram is `<w>.in_gram`. Failing that, it's `<owner>.in_gram` through the
  alias arrays.
- **The owner** is the first weight of the group in loader order, so it doesn't depend on graph
  build order.
- **Both triangles are stored,** as a plain `[n, n]` matrix that any tool can read in row slabs.
  - Packed triangles would save 50 GB, but each would become a flat 1D tensor with strided rows.
  - A converter can be added if disk becomes the limit.
- **Every KV has a fixed size,** so the header is written once before any data and rewritten in
  place at the end of each pass.

### 4. Capturing GEMM inputs (graph hook)

- **What's recorded:** `llama_cparams::collect_mm_inputs` (default off) makes `build_lora_mm` and
  the direct `rotate_input_if_rotated` call sites record `(x, w)` in the graph result. Here `x` is
  the unrotated input node and `w` the weight. Records with the same `x` form one group.
- **How the tool turns it on and reads it:** through an internal setter and accessor on
  `llama_context`. The tool links the internal headers, as tensor-kl does, so the public API
  doesn't change.
- **The accessor also gives the current ubatch's positions and sequence ids.** The hybrid memory
  reorders tokens into equal-length ubatches, so this is how the tool maps rows to count spans.
- **With the flag off, nothing changes.** With it on, the graph is identical too: only a side table
  is filled.
- **The callback:**
  - `ask` returns true for every recorded `x`, in every pass. Graph views, fusion boundaries and so
    the activations are then identical whichever layers a pass accumulates, which makes passes
    bitwise-invariant (Phase 4).
  - `observe` runs right after `x` is computed, so `x` is intact. It accumulates only if `x`'s
    group belongs to the current pass.
- **A recorded `x` must be a computed node** (not a leaf), F32, with `nb[0] = 4` and a uniform row
  stride. Otherwise the tool copies it to a contiguous buffer, or refuses a leaf with a message
  naming the weight.
- **Coverage check:** at the end, every 2D `blk.*` weight and the LM head must have a record,
  `blk.<nextn>` excepted. A weight that some architecture multiplies outside `build_lora_mm` is
  reported by name.

### 5. Accumulation

- **CUDA path:** one F32 `n × n` accumulator per group of the current pass.
  - For each counted row range, `observe` calls
    `cublasSsyrk(UPPER, N, n, k = rows, 1, x, lda = nb[1]/4, 1, G, n)` on `x->data` directly: the
    scheduler has already synchronized the backend.
  - The tool then synchronizes its own stream before returning, because ggml may overwrite `x`
    afterwards.
  - If `x` is in host memory, it's copied to a device staging buffer first.
  - The handle's math mode is pinned to plain FP32 (no TF32).
- **CPU path:** fp64, multithreaded blocked loops. It's used for tests and for CPU-only builds on
  small models, and it's the reference that Phase 4 compares the GPU against.
- **Precision:**
  - Within a SYRK, fp32 sums over up to 8192 rows; then a few hundred ubatch adds.
  - The expected error is about 10⁻⁶ of `√(G_ii·G_jj)` per entry. Sampling noise at 1M tokens is
    about 10⁻³, a thousand times more.
  - Phase 4 measures it against the fp64 path.
- **At the end of a pass,** each accumulator is:
  - downloaded (at most 1.21 GB of host memory, for `ffn_down`)
  - mirrored upper → lower in tiles
  - checked finite, and its diagonal checked non-negative
  - written with `pwrite` at the tensor's offset
  - `in_sum2 = diag(G)` and `counts` are written with it, for the group's owner and its aliases
- **Cost:** the SYRKs total `Σ n²/2` multiply-adds per token, which is 25 GFLOP per counted token
  and 25 PFLOP for the set. At an assumed 50 TFLOP/s sustained F32, that's about 8 minutes,
  whatever the number of passes.

### 6. Passes, placement and memory

**Placement for the 27B run:**
`-ngl 99 -ot 'blk\.[0-9]+\.ffn_(gate|up|down)\.weight=CPU,blk\.64\.=CPU' --no-mmap -ctk q8_0 -ctv q8_0`
- **FFN weights:** the 18.2 GB stay in RAM, and op offload streams them to the GPU once per
  8192-token ubatch.
- **Everything else stays on the GPU:** attention and DeltaNet weights, the KV cache, the recurrent
  states and `output`. So attention over long contexts stays off the CPU.
- **`--no-mmap`** loads the weights into ordinary memory, where the page cache can't evict them.
  `--mlock` isn't an option at this memlock limit.
- **The unused MTP layer `blk.64`** stays on the CPU.
- **The KV cache is q8_0,** so that 64k sessions fit the budget below. That's closer to the
  unquantized model than the user's q5_1.

**VRAM budget** (Phase 4 replaces the estimates with measurements):

| item | GB |
|---|--:|
| free on the 5090 | 29.9 |
| non-FFN weights + `output` | −9.0 |
| compute buffer, 8 recurrent states, 1 GB logits (estimate) | −4.5 |
| KV cache, 16 layers × 65536 cells, q8_0 | −2.3 |
| left for accumulators | ≈ 14 → **8 layers × 1.573 GB** |

- **Passes:** ⌈64 / 8⌉ = 8. `output` joins the last pass.
- **Sizing:** the tool picks the group size from `cudaMemGetInfo` after creating the context, with a
  1 GB margin. `--group-layers N` overrides it.
- **Host RAM:** 18.2 GB of FFN weights + 1.35 GB `token_embd` + at most 1.2 GB for downloads, which
  is about 21 of 30 GB.
- **Analysis scripts on the 101 GB file must read row slabs.** A 27B broadcast has OOM-killed a
  session before.

**Batching:**
- **Packing:** documents of at most 8192 tokens are packed whole into batches of at most 8192
  tokens and at most 8 sequences. Each document is its own `seq_id` with positions from 0.
- **Similar lengths go together.** The hybrid memory cuts a batch into ubatches with equal tokens
  per sequence, so a 3k document packed with a 5k one would run as a 6k ubatch plus a 2k ubatch.
- **Longer documents** (OpenCode) run alone, as consecutive 8192-token ubatches of one sequence, so
  their KV cache and recurrent state carry across them.
- **Decode calls:** the tool calls `llama_decode` once per packed batch or long document
  (`n_batch = n_ubatch = 8192`, `n_ctx = 65536`, `n_seq_max = 8`) and clears memory after each.
- **Pack order is fixed** (sorted by id within length buckets), so passes and resumed runs see
  identical ubatches.

**Time** (estimate):
- **Processed tokens per pass: about 1.45M.** That's the 1.0M counted, plus OpenCode's shared
  prefix in the documents where it isn't counted (about 0.33M: 30 documents × 11k), plus the
  uncounted first halves of the long sessions (about 0.1M).
- At about 2,000 tokens/s (18 GB of weight streaming plus 27B of compute per 8192-token ubatch), a
  pass takes about 12 minutes, so 8 passes take about 1.6 hours.
- Add about 8 minutes of SYRK, about 2 minutes of writes (101 GB) and the model loads.
- **Sharing the prefix would cut about a fifth:** decode the shared prefix once, then copy its KV
  and recurrent state to the other sequences with `llama_memory_seq_cp`. It's an optional Phase 4
  optimization, taken if `seq_cp` works for this model's hybrid memory.

### 7. The tool

```
hessian-collect -m MODEL.gguf --docs CALIB.jsonl -o OUT.gguf
    [-ngl N] [-ot REGEX=DEV] [--no-mmap] [--ubatch 8192] [--ctx 65536] [-ctk q8_0 -ctv q8_0]
    [--max-seqs 8] [--output-stride 8]
    [--group-layers N|auto] [--layers A-B] [--resume] [--imatrix-out FILE]
    [--text FILE --chunk N]          # upstream llama-imatrix-style chunks of one text, for tests
```

- **Tokenization:** `parse_special = true`, so template tokens stay single tokens, and the vocab's
  own BOS rule applies (Qwen adds none).
- **Mapping:** a 64-token dry decode records the groups and shapes. The tool then writes the header
  and allocates the file (`fallocate`).
- **`--resume`** reads `hessian.layers_done` and skips finished layers. The data order is
  deterministic, so a resumed run writes the same bytes.
- **`--layers A-B`** collects a subset (Phase 5's diagnostics).
- **`--imatrix-out`** also writes the diag-only imatrix from the same run.
- **Progress:** per pass, tokens/s, SYRK time and write time; at the end, peak VRAM and RSS.
- **Build:** Makefile targets `hessian-collect` and `hessian-collect-cuda`, linked like
  `tensor-kl` / `tensor-kl-cuda`.

### 8. Loaders

- **`common_imatrix_load`** opens GGUFs with `no_alloc = true` and reads only the `.in_sum2` and
  `.counts` data, from their file offsets. Behaviour on ordinary imatrix files is unchanged.
- **New `common/hessian-loader.{h,cpp}`:** open a file; `has(w)`, `n(w)`, `owner(w)`, and
  `read(w, float * dst)`. The read goes through `pread` into the caller's buffer, and the rows can
  come in slabs. The next plan's quantizer uses it.

## Phase 1 — Calibration set (`tools/hessian/calib/`)

   per dataset, pinned by revision (PG-19 and FineWeb-Edu are never downloaded whole), and the code
   repos at fixed commits with their licence files.
2. **`prompts.py`** builds the prompt list per category, with categories, languages and the
   thinking mix sampled from a fixed seed.
3. **`generate.py`** renders each prompt as koboldcpp does, posts it to the raw completion endpoint
   (8 parallel requests), filters bad generations and appends the finished document. It can be
   resumed (state in `work/gen/`). Multi-turn conversations loop back through it.
4. **`raw.py`** cuts raw-text documents to the length distribution.
5. **OpenCode (§1.1, §1.2):**
   - **`opencode/setup.sh`** builds the isolated dirs and config and clones the working copies.
   - **`opencode/proxy.py`** is the logging proxy.
   - **`opencode/tasks.jsonl`** holds the session tasks and episode prompts, which the user

   - **`opencode/run.sh`** runs the sessions and episodes one at a time, with their follow-ups,
     deleting each working copy once its run is rendered (and on failure or interrupt, via a
     `trap`).
   - **`opencode/render.py`** turns each capture into its document and sets its count spans (the
     shared-prefix quota, the late half of long sessions).
   - **`opencode/evalset.py`** renders the user's recorded sessions into the evaluation set.
6. **`decontam.py`** does the 13-gram filter.
7. **`split.py`** makes the held-out split by source unit, writes the kept files to
   `tools/hessian/calib/dataset/` (first `build-hq/calib/qwen38-calib-v1/`) and the manifest with their sha256.
8. **`stats.py`** reports the checks below.
9. **`cleanup.sh`** removes `tools/hessian/calib/work/` once the checks pass, and lists anything left
   outside the kept paths.

**Checks:**
- Per-category counted tokens are within ±10 % of target, and the total is within 1.0–1.1M.
- No document exceeds 8192 tokens, except OpenCode sessions and episodes (65536).
- Count spans lie inside their documents and don't overlap.
- The shared prefix makes up 15–25 % of the OpenCode-related counted tokens.
- The episodes' tool calls are within 5 points of the target mix for bash, read, grep and edit.

  - the user's `~/.local/share/opencode/opencode.db` and `~/.config/opencode` are unchanged (row

  - the original repos are unchanged (`git status` clean, same HEAD)

- **Diagonal vs upstream:** `hessian-collect --text wiki.train.raw --chunk 512` on 20 chunks

- **Format:**
  - the loader reads back every Gram, and the aliases resolve
  - `in_sum2 = diag(in_gram)` bitwise
  - `G` is symmetric bitwise
  - the header parses with `gguf_init_from_file(no_alloc = true)`
- **Imatrix compatibility:** `quantize_gguf --hadamard --imatrix <hessian file> Q4_K_M` gives

- **Resume:** a run stopped after pass 2 (a test-only `--stop-after-pass`) and resumed gives a file
  identical to an uninterrupted run.
- **Count spans:**
  - A document counted as two complementary spans gives Grams that add up to the whole
    document's, within 10⁻⁶.
  - A span covering the whole document gives the same bytes as no span.
  - Packed with other sequences, a document's counted rows are the same as when it runs alone.

## Phase 5 — The 27B run

- **Run:** the full set on `Qwen3.8-27B-HQ8_0.gguf`, writing
  `~/Sandbox/unquantized/Qwen3.8-27B-gguf/qwen38-27b-hessian-v1.gguf` and, via `--imatrix-out`,
  `qwen38-27b-imatrix-v1.gguf`. Record wall time per pass, peak VRAM and RSS, and the file size
  (expected 100.8 GB).
- **Sanity checks,** streamed over the file:
  - All counts equal the counted-token total; `output` has about 1/8 of it.
  - Everything is finite.
  - The fp64 Cholesky of `G/mean(diag G) + 0.01·I` succeeds for every input of layers 0, 31 and 63
    and for `output`.
  - Per weight, the correlation of `log v̄` against `imatrix_unsloth.gguf` is recorded. Expect high
    agreement: same model, different text.
  - Channel 3994's share of the attention-input energy in early layers is recorded. The GPTQ plan
    measured 93–98 % from Unsloth's imatrix.
- **Split-half check** (Grams in `tools/hessian/calib/work/diag/`):
  - Collect layers 0, 31 and 63 (`--layers`) from two disjoint halves A and B of the set.
  - For each input, report `ε = ‖(G_B + λI)^{-1/2}(G_A − G_B)(G_B + λI)^{-1/2}‖₂`, with
    `λ = 0.01·mean(diag G_B)`, both Grams normalized by their counts. Also report the relative
    Frobenius difference.
  - These numbers go to the next plan. They're a diagnostic, not a gate: whether 1.0M tokens is
    enough is decided by held-out KL there.
- **Position check:**
  - Collect the same three layers from the OpenCode documents, with count spans limited to
    positions 0–8k, 8–32k and 32–64k.
  - Report `ε` between the buckets next to the split-half `ε`.
  - If position moves the Gram clearly more than sampling noise, the next version of the set
    shifts more share to long sessions.
- **Cleanup:** `cleanup.sh` removes the diagnostic Grams once the numbers are recorded. What
  remains is the calibration set, the evaluation set, the Hessian and its imatrix.

## Implementation record

Implemented 2026-09-27/28. Left uncommitted. Measurements are on this box (RTX 5090, WSL2, 30 GB RAM).

### Deviations and additions

**Calibration set (Phase 1)**
- **Tokenizer:** the scripts tokenize with a new vocab-only tool, `hessian-tokenize` (the same `llama_tokenize`
  call as the collector), not koboldcpp's `/api/extra/tokenize`.
  - koboldcpp's `token_count` writes one static vector, so concurrent calls corrupted counts (58 against 59), and
    its batch server died in `malloc` (heap corruption) while tokenize requests ran next to batched generation.
  - The endpoint also prepends BOS with `special: true`, which generation doesn't.
- **Generation robustness:** `generate.py` restarts a dead server and requeues its prompts, retries a full queue
  (503), requeues tokenizer errors (3 tries), holds a lock file (two generators once ran at once after a crash:
  30 duplicate documents removed), and drains on `SIGUSR1`. Lone UTF-16 surrogates in some source texts are
  replaced (koboldcpp can't encode them either).
- **Scheduling:** the held-out side is one pool per category (tiny per-language held-out buckets each got a whole
  document otherwise); a bucket starts another document only if it then likely ends closer to its target.
- **Loop filter:** a 64-token span occurring 3 or more times (twice is normal: code drafted while thinking, then
  given), and a compression ratio above 1.5 x the 95th percentile of the first 200 documents (4.71).
- **Capped replies are kept, truncated at the cap (the user's decision).** Replies hitting the 6144-token cap were
  44 % of generated tokens (85 % of xhigh coding). They pass the loop checks and end at the cap without
  `<|im_end|>`. `split.py` takes each bucket's documents in generation order up to its target, which is what the
  generator would have kept with this rule from the start. Truncated share: coding 56 %, math 44 %, long 34 %,
  chat 29 %.
- **Long-context prompts** are 4-5.5k tokens (documents 6-8k): 6-6.4k prompts left under 2k tokens for the reply.
- WildChat chat and coding prompts are English only (multilingual covers the rest).
- **OpenCode, sandboxed:** each run is in a user and mount namespace that overlays `$HOME` with a throwaway layer in
  /tmp, with the isolated XDG dirs mounted through. The working copies live in the layer and go with it; nothing
  the agent writes reaches the real files.
- **OpenCode config:** the user's own provider and model names (OpenCode writes them into its system prompt, so the
  ~11k-token prefix matches the user's except for the working directory), webfetch not denied (denying removes the
  tool from the prompt), and the provider's `timeout`, `headerTimeout` and `chunkTimeout` off or 1 h: koboldcpp
  sends a tool-mode reply only when it's complete, and OpenCode retried any reply over 5 minutes from scratch.
- **`opencode run` needs `< /dev/null`:** with a piped stdin it waits for EOF to read the message, which hung runs
  started from a shell with an open stdin (and would have swallowed the follow-up prompts in the `while read` loop).
- **128k context instead of 64k (the user's decision):** 19 of the user's 44 recorded Qwen3.8 sessions go past 64k
  (7 past 128k, the longest 232k). Server, proxy, OpenCode `limit.context` and the collector's `--ctx` are 131072.
- **Context overflow:** OpenCode sizes sessions from `usage`, which koboldcpp's streamed tool replies don't carry,
  so it never compacted, and koboldcpp silently cut the prompt's start to fit. The proxy now returns OpenAI's
  `context_length_exceeded` when prompt + `max_tokens` exceeds the context; OpenCode then compacts.
- **Prompt-token check from the server log** (`CtxLimit - Generated` per request), since tool replies carry no
  `usage`: 644 captured requests, all equal to the rendered prompts.
- **Chains:** a compaction (or a subagent) starts a new history, so each chain of requests extending one another is
  rendered as its own document; `split.py` keeps each session's longest chain (a document costs its whole length
  in every pass, counted or not).
- **Counted-position budget (`split.py`):** the sessions ran long at 128k (one chain of the 11 sessions alone counted
  90k), so counted positions are thinned in 512-token blocks at a fixed stride over each document's counted range
  (long sessions: positions >= 32k, 40 % of the category; other sessions: after the prefix, the rest). The three
  documents that count the shared prefix keep it whole. Episodes are thinned to their half of the agentic category.
- **Kept:** `eval-opencode.jsonl` holds 34 of the user's sessions (2.28M tokens). s01's raw capture was overwritten
  by a restart (its rendered documents and checks are intact).

**Collector (Phases 2-4)**
- **Packing pads** each document of a batch after its end to the batch's longest, with uncounted pad tokens: the
  hybrid memory's equal-length split otherwise makes one ubatch per length difference, each streaming the FFN
  weights again. Counted rows are bitwise the same packed or alone.
- **Coverage** is checked on the graph: every weight that is `src0` of a `MUL_MAT`/`MUL_MAT_ID` must have a record
  (`ssm_conv1d` is 2D but no GEMM). Every ubatch is also checked token by token against the batch the tool built,
  which validates the accessor's positions and sequence ids on every run.
- **Added:** `--dry-run`, `--test-hook`, `--no-op-offload`, `-ot ...=CUDA_Host`, `hessian-tokenize`,
  `tests/test-hessian.cpp`, `tools/hessian/analyze.py`.
- **Makefile:** `llama-model.o`, the gpttype adapter, tts and embeddings objects didn't depend on
  `src/llama-graph.h` / `llama-cparams.h` / `llama-context.h`; after the hook changed those structs, stale objects
  crashed koboldcpp. The dependencies are added.
- Under WSL `cudaMemGetInfo` doesn't count other processes' allocations: `--group-layers auto` is only valid with
  nothing else on the GPU.
- Prefix sharing (optional) was not built.

**Test tolerances changed**
- **Diagonal against upstream:** per-weight relative L2 <= 5e-3, not 1e-3 per element. Measured 1.25e-3 worst
  (blk.11.ffn_down); the largest element-wise difference is 2.6e-2 (blk.27.ffn_down). Upstream 53ed051 runs other
  CPU kernels, so activations drift apart slowly with depth.
- **Natural space:** relative Frobenius <= 0.15 per Gram, not 1e-2 per entry. Measured 0.020 at layer 0 to 0.084 at
  layer 27 (quantization noise growing with depth). A random rotation of the BF16 Gram gives 1.41. The entry metric
  reaches 1.3 on a near-dead channel.
- **GPU fp32 against CPU fp64:** 5e-5 per entry, not 1e-5. Median 1.4e-8, 99.99th percentile 6.7e-7, max 1.8e-5
  (11 of 441M entries above 1e-5), relative Frobenius 6e-6.

## What comes next (separate plan)

- **`quantize_gguf --hessian FILE`:**
  - the HQ types use GPTQ with `H = R·(G/mean(diag G) + damp·I)·Rᵀ`, which needs a real Cholesky in
    place of the GPTQ plan's closed-form inverse, roughly 3× the factor time
  - the plain types use GPTQ in natural order, to test the finding that Unsloth's UD files look like
    plain quantization + full-covariance GPTQ
- **A/B,** all from this one file (its `in_sum2` is the diagonal baseline), comparing:
  - full-`H` GPTQ
  - diag GPTQ
  - UD-Q4_K_M
- **Evaluation sets,** in this order of weight:
  1. **`eval-opencode.jsonl`,** the user's recorded sessions, windows up to their real lengths.
     They're the closest thing to the user's use, and none of their text is calibrated on.
  2. **The held-out chat documents** from `calib-heldout.txt`.
  3. **wiki.test and tech-eval,** for out-of-domain drift.

  `calib-heldout` alone would flatter full-`H`, since it comes from the same sources as the
  calibration.
- **Tool-call validity:** re-run held-out OpenCode tasks with each quant and count unparseable tool
  calls, loops and unfinished sessions. KL can miss broken tool-call syntax.
- **Shrinkage against overfitting:** quantize with `H_α = (1 − α)·G + α·diag(G)`, with `α` and the
  damping chosen by KL on evaluation set 1.
  - `α = 1` is today's diagonal GPTQ, so an honest choice of `α` can't do worse than now.
- The GPTQ plan's low-rank variant can be computed offline from the same Grams.

## Follow-up: full-Hessian GPTQ (2026-09-28)

Done from the list above: `--hessian` for the HQ types, shrinkage, and the A/B on evaluation sets 1–3 (not
tech-eval). Not done: GPTQ for the plain types, tool-call validity, the low-rank variant.

- **Quantizer:** `quantize_gguf --hadamard --hessian FILE [--hessian-alpha α]` (`tools/quantize/README.md`, "With a
  hessian file"). `H = R·((1−α)·Ĝ + α·diag(Ĝ) + damp·I)·Rᵀ`, `Ĝ = G/mean(diag G)`. GPTQ needs `U` upper with
  `H⁻¹ = UᵀU`: with `J` the index reversal, the Cholesky `J·H·J = WᵀW` gives `U = J·W⁻ᵀ·J`, and `W⁻ᵀ` comes out of
  one Cholesky pass over `[J·H·J | I]` (`gptq_cholesky` gained a row stride and an augmented mode). 11 s at
  `n = 17408`, `20·n²` bytes. The Gram reader moved to `src/llama-hessian.{h,cpp}` (`llama_hessian`).
- **Tests (`test-hq-gptq`):** a diagonal Gram and `α = 1` reproduce the imatrix factor (max `|ΔU|/max|U|` 6e-8);
  `U·H·Uᵀ = I` within its bound for random Grams (rank n/8 and full, `α` 0 and 0.5, damp 0.001–0.1) and for
  diagonal-plus-rank-one Grams at `n = 5120` and `17408`; refusals, thread invariance and the cache.
  End to end on Qwen3-0.6B (Q4_K_M, wikitext calibration and test): `α = 1` changes 0.2 % of the bytes of
  `--imatrix` GPTQ and the same KL (0.0421 vs 0.0419); `α = 0` 0.0319, `α = 0.25` 0.0273, `α = 0.5` 0.0290.
- **Evaluation harness:** `tools/hessian/eval/` (`ref.sh`, `eval.sh`, `iter.sh`, `queue.sh`, `compare.sh`; see its
  README; first `build-hq/hessian-eval/`). BF16 reference
  log-probs with `test-hadamard-ppl-cuda --ref-ngl 33` (2 min per set); each model at `-ngl 99`.
  - wiki: wikitext-2 test, 80 × 512
  - heldout: the 45 held-out documents, 9000 characters each, 64 × 1024
  - opencode: a 9000-character slice (from a turn start) of each of the user's 34 sessions, 36 × 2048

  nats) against 0.009 on wiki. Chat models are trained only on their own turns: in user and tool turns both

  only assistant turns and text outside turns (19k of 33k heldout and 15k of 37k opencode positions).

- **Conclusions:**
  - Full-`H` GPTQ beats the diagonal on every set at α ≤ 0.1 (geomean 0.77–0.81 against 0.90), and beats
    UD-Q4_K_M at the same size by 29–36 % on heldout and 20–33 % on the user's sessions.
  - Below α = 0.1, α and the damping (0.003–0.1) are within the noise of these sets: neighbouring settings swap
    places set by set, by up to about 10 %. α = 0.25 is clearly worse, so the Phase 5 worry about poorly
    determined directions doesn't call for heavy shrinkage at 1M tokens.
  - Best: **α = 0.1, damp 0.01** (geomean 0.770, wikitext +1 % vs UD), now `--hessian-alpha`'s default.
  - Wikitext stays behind UD (+1 to +12 %): the calibration set has little wiki-style prose.
- **Next:** GPTQ for the plain types in natural order, tool-call validity runs, and more wiki-style text in the
  calibration mix.

## Future work

- **Early exit:** a scheduler abort (the callback's `false` stopping the whole graph, not one
  split) would skip the layers after the pass's group, about 45 % of the forward cost.
- **Tile-packed accumulators:** upper-triangle 1024² tiles via batched GEMM halve accumulator VRAM,
  which means 4 passes instead of 8.
- MoE (`MUL_MAT_ID`) Grams per expert, MTP layers, vision documents.

## Risks

- **RAM pressure:** the FFN weights (18.2 GB) must stay resident. Evicted pages would be re-read
  from disk for every ubatch. Mitigations: `--no-mmap`, nothing else large running, and Phase 4's
  RSS measurement.
- **Op-offload throughput:** if Phase 4 shows the weight stream dominating, try host-buffer
  registration (pinned memory) or a larger ubatch.
- **The size of the output (101 GB, 288 GB free):**
  - a failed run can resume (`--resume`)
  - nothing may read the whole file: the loader and the analysis scripts work in slabs
- **An agent running shell commands:** the OpenCode runs execute whatever HQ8_0 decides to run.
  Mitigations:
  - disposable clones without git remotes, deleted after each run
  - a permission deny list, and no network for package managers
  - isolated OpenCode dirs
  - Phase 1's checks that the user's data and the original repos are untouched
- **Calibration bias:**
  - Everything the model generates comes from one model at its own sampling settings. Real usage
    has user-written text too, which the prompt sources, raw text and tool outputs supply.
  - Contexts past 64k aren't represented; the position check says whether that matters.
- **Overfitting of full-`H` GPTQ:** addressed in the next plan by shrinkage toward the diagonal,
  tuned on the user's recorded sessions rather than on data from the calibration sources.
- **Silent wrong-data hazards, each with a test:**
  - capturing the rotated input (natural-space test)
  - an overwritten `x` (fp64 reference and upstream diagonal agreement)
  - a missed weight (coverage)
  - pass-dependent activations (pass invariance)
  - rows mapped to the wrong count span (count-span tests)
  - alias or offset mistakes in the file (round trip)
  - prompts rendered differently from koboldcpp (token-count check)
